## Native numeric-coercion variant review

The root cause was converting unreadable native data with `Number()` before deciding whether it
matched desired state. `null`/false/empty data could become zero; other coercible data could become
an apparently valid native speed, measure or preset identity. Native source types and retained phaser
probe definitions require numbers for those fields. Cue-part display numbers additionally accept
explicit decimal strings through a bounded parser.

Searches ran over the source tree at the previous commit, expanding from the exact speed-master
expression to related stored fields and native identities. Seven coercion expressions were confirmed
across the verifier and cue inspector. This was a bounded correctness review, not a whole-repository
security certification.

| Pattern level | Baseline matches | Verdict |
| --- | --- | --- |
| Exact `Number(actual.stored.speedMaster)` | 1 | High impact, proved false verification |
| `Number(actual.stored.<field>)` | 3 | High impact, speed/measure/master variants proved by regression |
| `Number((actual.stored\|link\|item\|row).<field>)` | 7 | Added preset identity and Part 0 association variants |

The search needed a word boundary: an unanchored `Number(` also matches the safe helper name
`nativePartNumber(`. Desired cue numbers intentionally use validated numeric strings; their conversions
were retained. Static/native step comparisons already require finite numeric values. Existing native
default/tolerance behavior remains a separate qualification boundary.

The regression files run in normal CI. A narrow additional CI-ready search rule for these typed
source fields is:

```sh
if rg -n '\bNumber\((actual\.stored|link|item|row)\.[A-Za-z]+\)' src/native-cue-verification.ts src/tools/inspection.ts; then
  exit 1
fi
```

The helper's explicit decimal-part parser remains permitted. No new lint dependency was introduced.
